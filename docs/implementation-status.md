## 缺陷修正

本次新增的审批与运营查询集成测试在结束时释放其创建的 assignment/Offer 并下线临时骑手，避免共享 H2 数据影响后续用例。Outbox 测试夹具把新事件的 created/next-attempt 时间设在当前时间之前一秒，避开 TIMESTAMP(3) 向上舍入导致新事件短暂不可领取的边界。

Consumer DLQ Lua 先前在写入 Stream 后才更新去重 Hash；Hash 键类型错误时，Lua 命令错误不会回滚之前的 XADD，可能留下半写入。脚本现先校验 Stream/Hash 键类型，并在去重标记更新失败时删除本次 Stream 记录；故障用例断言 DLQ 写失败时源消息仍 Pending 且 DLQ Stream 为空。

限流过滤器此前只从 POST JSON 请求读取区域，导致 PUT presence 请求进入全局 `all` 区域桶；现对 JSON 请求统一提取 `regionId`，并增加 PUT 区域维度测试。Redis 命令异常在过滤器外层曾重复计一次错误，现只由命令计时边界记录一次，并由回归测试校验计数。

真实 MySQL/Redis 套件的 `acceptAndTimeoutAtExpiry_competeThroughOfferRowLock` 曾在启动竞争前就把 Offer 设成过期，实际只验证过期拒绝；现改为两个事务同步等待到期时刻后争用同一 Offer 行锁，并断言只发生超时、没有 Assignment，且容量台账保持一致。该用例本次因 Docker 不可用而 **NOT RUN**，构建只验证了编译。每个真实设施套件用例都会核对 capacity limit、活动 Offer/Assignment 与数据库台账，并检查每个订单最多一个活动 Offer/Assignment；旧代次、重复消费及补偿幂等由对应场景单独断言。

完整测试还暴露 `TIMESTAMP(3)` 对 `.999600` 秒向上舍入，可能令刚创建订单的 `next_dispatch_at` 短暂晚于应用时间并返回 `STALE_ORDER`；[JdbcDispatchRepository.java](../peakdispatch-infrastructure/src/main/java/com/peakdispatch/adapter/mysql/JdbcDispatchRepository.java) 现将初始派单时间向下截断到毫秒，并由 `initialDispatchTime_isFlooredToDatabaseTimestampPrecision` 覆盖。P0 测试夹具也改为按订单 ID 推进，避免共享 H2 数据中超过 100 条旧订单时目标测试订单留在 `CREATED`。这些 H2 回归结果仅作为普通测试结果，不是 MySQL 证据。
