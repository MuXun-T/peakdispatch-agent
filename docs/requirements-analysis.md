## 1. 文档目的

本文定义峰配调度 Agent 的业务目标、系统边界、功能需求、质量要求、关键数据与验收方法，并按软件工程 V 模型建立需求到测试的追踪关系。它是后续总体设计、接口设计、实现、测试和项目演示的共同依据。

本文是项目设计基线。四类负载已在隔离仿真环境完成实测，当前性能验收采用 `agent-support-baseline-v1`，用于确认后端足以支撑 Agent；严格生产级派单时延目标保留为后续优化目标。

## 2. 项目背景与参考原则

午晚高峰的即时配送会同时受到订单突发、商家备餐延迟、骑手位置变化、骑手拒单和订单时限等因素影响。运营人员需要快速发现履约风险并做出调度决策；系统则需要在高并发下保持订单分配正确、状态可恢复和操作可追踪。

本项目借鉴 [TaxiAgent](https://github.com/ZhuofanWu/TaxiAgent) 的工程思路：Java/Spring 后端、领域化 Agent、业务工具调用、关键操作人工确认、对话与运行状态持久化、知识检索，以及 Redis 服务真实业务并发的实践。项目自身聚焦外卖履约：商家备餐、骑手多单容量、拼单、送达时限和运营异常。LLM 不进入逐订单的实时派单热路径；实时派单由可测试的调度服务完成，Agent 面向调度员提供解释、查询、模拟和受控操作。

## 3. 项目目标与范围

### 3.1 项目目标

1. 构建可模拟商家、骑手、外卖订单和运营调度流程的履约系统。
2. 使用 Redis 支撑订单事件消费、附近骑手索引、运力预占、超时重试和限流。
3. 为运营调度员提供可调用业务工具、可检索 SOP、可请求确认的调度 Agent。
4. 用可复现仿真与并发测试验证业务效果、状态正确性、系统吞吐和 Agent 工具质量。
5. 形成能够在面试中演示和解释的工程项目：业务闭环、架构图、测试报告、指标面板和失败恢复过程。

### 3.2 范围内

- 外卖订单生命周期、商家备餐状态、骑手在线与位置、派单和骑手接单/拒单。
- 基于地理范围、备餐时间、预计送达时限和骑手容量的候选筛选及派单策略。
- 多订单拼单的方案预览；MVP 先以确定性规则评分为主。
- 运营 Agent 的自然语言查询、订单诊断、调度模拟、SOP 问答和受控异常操作。
- 人工确认、幂等执行、审计记录、运行历史和指标统计。
- Redis Streams、GEO、ZSet、Hash、Lua 等能力在业务链路中的实际应用。

### 3.3 范围外

- 真实支付、消费者营销、商家结算、骑手工资和补贴结算。
- 真实地图导航和道路交通预测；MVP 使用模拟距离/路线服务或地图服务适配器。
- Agent 自动执行代码、任意 Shell 命令或未经确认的批量取消/改派。
- 直接连接真实外卖平台生产账户。
- 以 LLM 替代派单状态机、容量约束或路径规划算法。

## 5. 典型业务场景

### UC-01 高峰订单自动派单

订单创建后进入待派队列。调度服务从订单所属区域和相邻服务区查找候选骑手，结合距离、预计出餐时间、剩余携单容量和订单截止时间计算候选分。系统短时预占候选骑手容量并向骑手发送派单；骑手接单后确认分配，拒单或超时则释放容量并进入下一轮调度。

### UC-02 运营查询区域风险

调度员询问“现在滨江区哪些订单可能超时”。Agent 解析区域与时间范围，通过指标工具读取待派订单、订单剩余时间、在线骑手和商家备餐状态，检索相应运营 SOP，按订单列出风险原因与可操作建议。回答需标明数据时间和来源。

### UC-03 诊断单笔订单

调度员询问某订单为何没有骑手接单。Agent 读取订单事件、派单轮次、候选骑手和商家预计出餐时间，并用 SOP 检索解释可能原因。没有证据的数据不得由模型补写。

### UC-04 模拟并确认改派

调度员请求重新分配高风险订单。Agent 调用调度模拟工具生成候选方案及影响，不直接修改订单。调度员确认后，业务服务检查订单版本、状态、权限和幂等键，再执行改派并写入审计记录。

### UC-05 骑手拒单或派单超时

拒单/超时事件被幂等处理，系统释放对应预占，更新订单状态并重新加入调度流程。重复事件不得造成重复派单、重复释放容量或非法状态回退。

## 7. 业务规则与状态约束

### 7.1 订单状态

```text
CREATED -> WAITING_DISPATCH -> OFFERED -> ACCEPTED -> PICKED_UP -> DELIVERED
                                  |            |
                                  |            +-> WAITING_DISPATCH（允许改派时）
                                  +-> WAITING_DISPATCH（拒单/超时）
任意未完成状态 -> CANCELLED（受取消规则和权限约束）
```

- 状态由业务服务统一流转，Agent 不能直接修改状态字段。
- 每次状态变化携带事件 ID、操作者、时间和前后版本。
- 订单版本用于数据库条件更新，避免并发覆盖。
- 同一订单只能存在一个有效接单结果；超时的旧派单令牌不得再确认。

### 7.2 运力约束

- 骑手必须在线且心跳未过期，才可参与候选计算。
- 骑手的已接订单数加上有效预占数不得超过配置容量。
- 候选分至少考虑骑手到商家的距离、预计出餐时间、订单剩余时限和骑手负载。
- 规则权重与阈值版本化，调度结果可记录使用的规则版本。
- 拼单必须通过容量、取餐顺序和送达时限检查；不满足硬约束的候选方案不得执行。

### 7.3 Agent 确认状态

```text
AgentRun:
RUNNING -> WAITING_CONFIRMATION -> RUNNING -> COMPLETED | FAILED | CANCELLED

AgentAction:
PENDING_CONFIRMATION -> CLAIMED -> COMPLETED | FAILED
PENDING_CONFIRMATION -> REJECTED | EXPIRED | INVALIDATED
```

- 待确认动作持久化保存，Redis 可缓存短期确认令牌，但不能成为唯一记录。
- Run 与 Action 状态独立；Action 每种终态均持久化为可恢复事件，Run 按 checkpoint 恢复并向用户返回结果。
- 确认操作必须校验动作 ID、认证主体、动作摘要、订单版本、有效期和幂等键；演示审批主体须与申请人不同。
- 用户拒绝、确认过期或业务状态已变化时，不得执行原动作；对应终态仍须恢复等待中的 Run。

## 8. Redis 高并发与一致性需求

| 数据结构/机制 | 业务用途 | 正确性要求 |
|---|---|---|
| Redis Streams + Consumer Group | 承接订单派单、骑手状态、超时等事件 | 消费至少一次；消费者必须幂等；Pending 消息需可恢复 |
| GEO | 按地理范围查找骑手候选 | GEO 仅作候选索引；候选最终状态需复核 |
| ZSet 心跳索引 | 记录骑手最后心跳并清理过期成员 | 不把 GEO key 整体 TTL 当作成员过期机制 |
| Hash | 保存短期运力计数、派单状态和预占信息 | 定义过期、恢复和与数据库对账方式 |
| Lua | 在单骑手 hash slot 内原子验证 presence、容量投影和短租约预占 | 不验证订单状态；订单状态、活动 Offer 和容量最终由同一 MySQL 事务仲裁；脚本有边界测试且失败不可留下永久占用 |
| ZSet 延迟索引 | 派单超时、重新评估和补偿任务 | 任务认领幂等；过期任务可重试或转死信 |
| Lua 限流 | 限制运营 API 和模型调用频率 | 限流按用户/角色/区域分维度；模型故障不导致无限重试 |

订单数据以 MySQL 为准，Redis 是高频索引、队列和短期协调层。订单创建与事件发布使用事务 Outbox，避免“数据库已提交但事件未发出”的双写丢失。Redis 预占使用带超时的 lease；数据库条件更新成功后由后续事件确认 Redis 状态。数据库更新失败、超时或实例崩溃时，释放 lease 或由对账/补偿任务修复。

演示使用单 Redis 主节点；key 仍须保持 Redis Cluster 可用的同槽契约：环境名是普通 `pd:<env>:` 前缀，hash tag 仅用于骑手、区域或延迟队列实体。rider-scoped Lua 的全部 keys 同属 `{<env>:<courierId>}`；订单 key、区域索引和全局 Stream 不传入该脚本。区域 GEO、版本 Hash 和 heartbeat ZSet 使用 `{<env>:<regionId>}` 同槽。Cluster-enabled 组件测试用 `CLUSTER KEYSLOT` 和实际脚本验证。关键履约事件不得只依赖 Pub/Sub。

骑手上线/重连/下线时由 MySQL 持久化递增 `presenceGeneration`；上线写入当前 `region_id`，在线会话变更写 `courier.presence_changed` Outbox，并通过幂等 presence 初始化投影后才向客户端返回 generation。重连/切区先清理旧 generation 的 presence，清理未确认前不报告新会话可用。心跳携带 generation 与该代次内从 1 开始严格递增的 sequence，构成 `presenceVersion=(generation,sequence)`；入口在 MySQL 事务中锁 courier 行并校验当前在线状态、代次和区域，再调用 rider Presence Lua，成功后提交并异步更新区域索引。上下线与心跳由同一行锁串行化；offline 事件异步失效对应旧 generation 的活动 Offer、释放 reserved 并重派，使用标准订单/容量锁序和 CAS。区域索引清理在旧区域 `versions` Hash 中保留 `(DB 当前 generation,0)` 删除 fence tombstone，禁止 `HDEL` 版本字段；因此已接受但延迟执行的旧心跳索引写不能在清理后复活 GEO/ZSet 成员。tombstone 在骑手仍有效期间保留。区域索引失败只允许漏候选。Redis presence key 缺失时 fail closed，必须显式重连取得新 generation。区域索引以复合版本比较更新 GEO/heartbeat；候选携带 `indexedPresenceVersion`，评分时核对 DB 在线/代次、Redis presence 和区域索引一致，rider Lua 预占时再次校验版本/区域；MySQL 创建及接受 Offer 时锁骑手行复核代次，Offer 保存创建时的 generation。旧会话或旧区域索引只能造成待过滤候选，不能用于有效 ETA 或 Offer。

## 9. 系统质量需求

所有目标为演示验收目标，固定基准为单机 Docker Compose、8 vCPU/16 GiB、单 MySQL 8.4 LTS、单 Redis 7.x 主节点、单区域和确定性模型/路线 stub；测试报告记录实际资源配置。该基准不代表生产容量承诺。

| ID | 质量属性 | 需求与验证方式 |
|---|---|---|
| NFR-PERF-001 | 性能 | `agent-support-baseline-v1`：错误率 <1%；稳态与规模场景订单速率达到目标的 99%，突发场景至少 140 单/秒；Worker 决策、Outbox 到结果持久化、Stream 入队到 Worker 开始处理 P95 均≤30 秒；突发积压 300 秒内清空。原生产目标 1 秒/2 秒/1 秒保留为观察项，模型耗时不计入 |
| NFR-PERF-002 | 高峰规模 | 单区域仿真至少 5,000 名在线骑手和 20,000 个订单事件；骑手每 30 秒均匀错峰心跳（约 167 次/秒）；均匀分布与 80% 集中于一个热点单元各跑一组。心跳频率是压测配置，不是业务 SLA |
| NFR-COR-001 | 正确性 | 并发测试中重复有效分配数、运力超限数、非法状态迁移数均为 0 |
| NFR-REC-001 | 恢复性 | Worker 重启、重复消费、Redis 短暂不可用后，未完成事件可恢复且不会重复执行业务效果 |
| NFR-SEC-001 | 安全性 | 用户和工具操作按角色授权；Agent 无直接 SQL、任意 Shell 或任意 URL 访问能力 |
| NFR-SEC-002 | 数据保护 | 密钥不进入 Git；日志中的手机号、地址和凭证按策略脱敏；生产数据与仿真数据分离 |
| NFR-OBS-001 | 可观测性 | 每次订单派单和 Agent 运行可用 trace/run ID 关联，记录状态、工具耗时、模型 token 和错误类型 |
| NFR-MAINT-001 | 可维护性 | 派单状态机、Redis key、Lua 脚本和 Agent 工具契约有集中定义与文档 |
| NFR-TEST-001 | 可测试性 | 仿真输入可固定随机种子；并发和故障测试可自动运行并输出机器可读报告 |

| Agent | Spring AI 兼容路线 | 模型调用、工具定义、结构化输出、流式事件和 Agent 编排 |
| 关系数据库 | MySQL 8.4 LTS | 用户、订单、骑手、派单、Outbox、Agent 运行和审计记录 |
| 高并发层 | Redis 7.x | Streams、GEO、ZSet、Hash、Lua、限流和短期状态 |
| 检索 | Elasticsearch（MVP 可先做 BM25，随后加向量检索与 RRF） | SOP 混合检索与引用来源 |
| 前端 | Vue 3 或 React | 调度台、订单/骑手视图、Agent 对话和确认面板 |
| 测试/部署 | JUnit、Testcontainers、Docker Compose、Gatling 或同类压测工具 | 单元、集成、并发、故障和可复现演示 |

技术基线为 Java 21、Spring Boot 3.5.x、MySQL 8.4 LTS、Redis 7.x；Spring AI 采用与 Boot 兼容的稳定版本，Redis 使用 Boot BOM 管理的 Lettuce。工程初始化时锁定补丁版本并做兼容测试。TaxiAgent 固定提交中的 `OrderGrabService` 仅展示 Lua 预检与数据库最终仲裁的实现模式，不是 Cluster 分槽或生产正确性的证明。

## 12. 数据对象草案

- `DeliveryOrder`：订单、商家、取送位置、预计出餐时间、截止时间、状态和版本。
- `Merchant`：商家区域、营业状态、备餐状态和平均备餐时间。
- `Courier`：骑手身份、当前服务区域、在线状态、持久化会话代次、当前位置、容量上限和当前负载。
- `DispatchOffer`：订单、骑手、创建时骑手会话代次、派单轮次、状态、租约截止时间和幂等键。
- `DeliveryEvent`：订单状态变化和外部事件的不可变记录。
- `DispatchPolicy`：派单规则、权重、适用区域和版本。
- `AgentRun` / `AgentAction`：Agent 输入摘要、工具调用、待确认动作和执行结果。
- `KnowledgeDocument`：SOP 元数据、版本、分块、检索索引和引用信息。
- `OutboxEvent`：与业务事务一同持久化、待发布到 Redis Streams 的事件。

## 14. 量化评估方案

### 14.1 派单业务指标

- 准时送达率、平均派单耗时、骑手等待商家出餐时间、每单空驶/绕行距离、拒单率、改派率、订单超时率。
- 对比基线：最近可用骑手优先；对比方案：加入出餐时间、订单截止时间和容量约束的候选评分/拼单方案。
- 使用固定随机种子和相同订单/骑手轨迹运行基线与新方案，输出指标差值和样本数量；不得把仿真改善描述成真实线上业务提升。

### 14.2 Agent 指标

- 工具选择准确率、工具调用成功率、区域指标回答与数据库基准值的一致率。
- SOP 检索 Recall@5/MRR、引用正确率、无依据问题安全拒答率。
- 高影响操作确认覆盖率、未授权写操作数（目标为 0）、Agent 平均耗时和单次模型成本。
- 建立至少 30 条带期望工具/正确答案/引用依据的运营问题集，并保留人工复核结果。

### 14.3 压测报告要求

每次报告记录基准主机与容器 CPU/内存、Java 堆、Redis/MySQL/ES 配置、数据规模、单区域均匀或 80% 热点分布、订单/心跳请求速率、并发数、热 key、P50/P95/P99、吞吐、错误率、Worker 决策耗时、Outbox 提交至结果的端到端时延、queue-wait、心跳时延、MySQL generation 校验查询量、Streams Pending/积压及数据库连接池状态。派单负载为 100 单/秒持续 10 分钟，另跑 200 单/秒 1 分钟突发；规模负载含 5,000 名在线骑手每 30 秒均匀错峰心跳（约 167 次/秒）。本轮四类场景已完成实测并保存原始结果，报告按 `agent-support-baseline-v1` 判定；严格生产级异步时延作为后续优化观察项。

## 15. 安全、权限与失败处理

- Agent 工具采用 allowlist；身份由服务端认证上下文提供，不接受模型自行指定 `userId` 或权限。
- 查询工具按运营角色和区域范围授权；批量改派、取消等工具在服务端校验权限和影响范围。
- 模型输出是非可信输入；必须通过结构化 Schema、业务校验和权限校验后才可执行。
- 知识库内容和订单文本视为不可信数据，不能覆盖系统规则或工具权限。
- LLM 超时或不可用时，派单业务继续运行；Agent 降级为明确的错误/只读查询，不影响订单热路径。
- Redis 不可用时停止新的 Redis 预占派单并保留持久化事件，待恢复后重放或对账；不得返回虚假的派单成功。
- 外部接口超时采用有限重试、幂等键和死信/人工处理，不对非幂等写操作盲目重试。

## 16. 风险与后续扩展边界

| 风险/假设 | 影响 | 后续处理 |
|---|---|---|
| 骑手位置与真实道路时间存在偏差 | 派单评分和时效估算不准确 | MVP 明确使用模拟距离；后续接入地图服务并分离接口适配器 |
| 仿真结果不等于生产效果 | 面试展示可能过度外推 | 报告注明数据来源和实验边界；不宣称未验证的线上收益 |
| Redis 预占与数据库状态可能短暂不一致 | 可能暂时占用运力或重放事件 | lease、Outbox、状态 CAS、对账和补偿测试 |
| 拼单问题复杂度增长 | 优化结果难解释或耗时增加 | MVP 限定订单数与硬约束；达到复杂度后评估 OR-Tools |
| 模型可能误解区域或订单指代 | 查询错对象或建议不适用 | 缺少关键槽位时追问；业务工具再次校验区域和权限 |
| 模型/向量服务成本与延迟变化 | Agent 体验不稳定 | 热路径不调用模型；设置限流、超时、缓存和用量记录 |

演示实现采用详细设计第 17 节的确定值：单区域、单人顺序邀请、固定仿真规模与 ETA、mock 模型和本地身份。跨区域调度、竞价、外部模型/地图、企业身份源和生产级高可用属于后续范围变更，不阻塞当前验收基线。

## 17. 交付与阶段建议

1. **阶段一：业务与 Redis 闭环**：订单状态机、商家/骑手模拟器、Outbox、Redis Streams、GEO 候选、Lua 预占、超时重试和并发测试。
2. **阶段二：运营 Agent**：工具 Schema、实时指标、订单事件查询、SOP 检索、SSE 事件、人工确认与审计。
3. **阶段三：量化与增强**：固定种子仿真、基线对比、压测报告、故障注入、拼单优化和面试演示材料。

阶段完成标准以本文需求 ID、测试报告和演示脚本为准。任何需求变更都应同步更新需求、验收用例和追踪表。
